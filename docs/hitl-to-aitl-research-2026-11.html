Research Report · Paradigm Shift

Human-in-the-Loop
→ Agent-in-the-Loop

迁移的本质不是「把人拿掉」，而是把人的位置从执行路径移到设计路径。人从逐动作批准，变成定义边界、验收标准与异常裁决。

本报告关注

Agent-in-the-Loop

目前没有统一术语。至少存在三种互不兼容的用法，只有第一种是 HITL 的直接对应物。

SENSE A · 运营范式

agent 主导，关键点咨询人

agent 规划、执行、适应；在边界内自主决策，关键动作找人。本报告采用此定义。[18]

SENSE B · 数据飞轮

人类客服在环

EMNLP 2025：在真实客服运营中采集四类标注，反馈训练模型。这里的 "agent" 是 human support agent。[22]

SENSE C · AIL-ML

人与大模型共同在环

Springer 2025：agent 同时指人与大模型，协作构建垂直模型。与 AI agent 治理无关。[23]

本项目工作定义：AITL = agent 是主要执行者；harness 负责验证、策略与升级；人类只在「不可逆、越界、定义缺失」三类点介入。它更接近 HOTL + agentic verification，而不是「无人」。[2][4][11]
Control Location

控制权在哪里

三种范式最直观的差别，不是「有没有人」，而是「人站在路径的哪个位置」。

HITL阻塞式
意图→ 人批准→ 执行→ 结果 每个高影响动作都要停；拒绝即中止
HOTL非阻塞
意图→ 执行→ 结果 人观察流，可随时打断；不打断则继续
AITL目标态
意图→ agent 规划→ 执行→ 自检→ 结果 仅在不可逆 / 越界 / 定义缺失时找人
关键纠正：HITL 不是「更安全」的同义词。看得越多，反而越不看——Anthropic 遥测显示用户批准了约 93% 的权限提示；医疗警报研究里 override 率 10 年升至约 88%。

Disagreements

四个真实分歧

这些不是「谁对谁错」，而是做插件前必须自己拍板的定义问题。

一方

AITL = 运营范式：agent 主导，关键点咨询人（agentintheloop.org，单一倡导站点）。[18]

另一方

AITL = 数据飞轮（EMNLP 2025）或 AIL-ML（Springer 2025），"agent" 甚至不是 AI。[22][23]

判断：术语未统一。项目内必须先写死定义，否则所有讨论都会漂移。

一方

CSA：L0–L5，L1 最严（逐动作批准），L5 全自主。[4]

另一方

云运维 rubric：L1 = 建议，L4 = 自主；AITL 2.0 又是另一套编号。[5][18]

判断：编号不可跨框架比较。只看机制：审批粒度、升级条件、执行边界。

一方

厂商按「模型能力」宣传自主等级：越强越自主。

另一方

Capability ≠ Permission：ACL 是技术能力，AAL 是组织授权，两者可长期分离。[6]

判断：不要用「模型变强了」推导「应该放开权限」。权限是治理决策。

一方

Karpathy / 部分 X 话语：agentic engineering，人应退出细节。[1]

另一方

HumanLayer / Fowler / Anthropic：人退出执行，但保留设计与验收。[9][11][2]

判断：当前证据支持后者。全退出的反例（lights-off 工厂）已有明确失败记录。[9]

Sequence

迁移顺序：不可跳步

直接从 L1 跳到 L4，是「lights-off 工厂」失败的标准路径。

STEP 1

写清 DoD

可执行、可判定、可否定。

没有它 → 全是主观判断
STEP 2

确定性验证

build / typecheck / lint / test。

没有它 → 无法判定完成
STEP 3

独立 verifier

对照 AC，不看执行者自述。

没有它 → 自报不可信
STEP 4

风险分类 + 升级

不可逆 / 越界 / 定义缺失。

没有它 → 无法安全放手
STEP 5

信任账本

慢授快收，迟滞防抖。

没有它 → 无法证明可放手
STEP 6

减少人工点

只减可逆、可验证的部分。

常见错误：因为模型变强了，从 L1 直接跳到 L4，跳过 2–5。HumanLayer 的 lights-off 实验就是这么失败的：代码库膨胀到 3–4 万行、出现复杂状态机，最终归档。[9]
Interactive

升级决策助手

选择动作属性，看看它应该自动执行、边界内执行，还是硬门禁。规则优先级：不可逆 > 风险 > 信任等级。

注意：信任等级只能放宽「可逆」动作；它永远不会为「不可逆」动作投票。
自动执行

自动执行 + 事后审计

可逆、低风险：让 agent 直接执行，记录审计轨迹，事后抽检。

Escalation

三类升级触发

AITL 的核心不是「不问人」，而是「只在正确的地方问人」。

① 不可逆[16][8]

无论信任等级多高，都必须硬门禁。

  • 删除、force-push
  • 付款、发邮件、改权限
  • 发布、合并主干

② 越界[4][7]

超出预先定义的边界，必须停下来。

  • 超出 owned_files
  • 超出预算 / 时间
  • 访问生产或新依赖

③ 定义缺失[11][2]

这是人真正的价值所在。

  • AC 冲突或歧义
  • 架构取舍无先例
  • 业务规则缺失
不属于升级触发：代码风格、命名、常规测试失败、可回滚的重构——这些应该由 agent 自修复，不应该消耗人的注意力。
Failure Modes

三种范式各自的失败方式

迁移不是消除失败，而是换一种失败方式。要选自己能承受的那种。

HITL阻塞式[3][14]

  • 批准疲劳（93% 批准率）
  • 人类漏检（13.6%）
  • 干预惩罚
  • 成为吞吐瓶颈
  • 自动化偏见
最坏情况：人以为自己在把关，实际上在盖章。

HOTL监督式[10][21]

  • 警报被忽略
  • 监控衰减为缺席
  • 标准本身写错
  • 事后才发现
  • 看板代替判断
最坏情况：on-the-loop 衰减为 out-of-the-loop，没人发现自己已经不在环里。

AITL自主式[13][8][9][24]

  • 自我报告造假
  • 不可逆动作越界
  • 代码库质量无快速 oracle
  • 信任分掩盖单次灾难
  • verifier 与 executor 同源
最坏情况：系统报告一切正常，而代码库已经在无人察觉中腐化。

八条设计规则

01

人类定义 DoD，agent 在 DoD 内自主[11]

人给标准，不给步骤。

02

权限与能力分离[6]

ACL 高不等于 AAL 高。

03

不可逆动作永在信任分之外[8][16]

可逆性是动作属性。

04

验证器独立于执行器[13]

不同上下文、不同证据。

05

完成由系统判定[4][7]

exit code / 产物 / 审计记录。

06

升级请求必须结构化[12][2][25]

尝试、证据、选项、推荐、置信度。

07

信任要慢授快收[7]

长窗口晋升、即时降级、迟滞防抖。

08

人工注意力是预算[3][14]

每个检查点都要问「值不值得一个人工回合」。

迁移的第一个可交付物：不是「自动批准」，而是一份机器可读的 DoD。有了它，agent 才能自检，harness 才能判定，人类才能退出执行路径。没有它，AITL 只是更快的失控。

Summary

一句话总结

Human → Agent 的迁移，不是把审批按钮交给 agent，而是把「判断是否完成」从人的直觉， 换成可执行的 DoD + 独立验证 + 风险升级； 人从执行路径退出，但保留边界设计与不可逆裁决。
