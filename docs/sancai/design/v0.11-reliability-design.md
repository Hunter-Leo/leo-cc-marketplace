# Sancai v0.11 可靠性设计：等待、派发、授权、验收

**Agent-in-the-Loop 的边界状态设计**

- 状态：Draft v0.11
- 日期：2026-11-25
- 依据：
  - `protein-studio` 会话 `697dbd46-ac09-42da-a68b-4e8b1631131c`（11-17 → 11-25，23,009 行）
  - `protein-studio` 会话 `3daceecb-584f-45b6-8dae-e500dbe40874`（命令路由问题）
  - `docs/sancai/design/loop-design.md` v0.4（整体架构，本文只覆盖 v0.11 增量）
  - 当前实现 `plugins/sancai-loop-plugin` 版本 `0.10.0-rc.7`
- 关系：本文不替代 v0.4。v0.4 定义 L3/L2/L1、H1/H2/H3、G0/G3、能力表与卡片绑定；本文只补齐 **等待、派发、授权、验收** 四个边界。

---

## 0. 北极星与范围

```text
Agent runs the loop.
Human designs the loop.
System decides when work is verified.
Human decides when the outcome is accepted.
Irreversible actions only leave through a human-minted capability.
```

本文只解决四件事：

| 边界 | 问题 | 本文机制 |
|---|---|---|
| 等待 | 人等 agent / agent 等人时，流程把等待当成失败 | `wait` + `lease` + Stop guard 决策树 |
| 派发 | 重复派发、旧消息重放、有 claim 无任务 | `dispatch` 幂等台账 + 租约回收 |
| 授权 | 决策已批准但 claim 未同步；reviewer 写盘被拒 | `authority = claim ∪ grants` + `role_outputs` |
| 验收 | 测试全绿但用户看到的输出是错的 | `observable` AC + 证据链 + H3 卡片 |

范围之外：不引入 daemon、SQLite、worktree、自动 merge 或自动 push。

## 1. 背景：protein-studio 的现场证据

### 1.1 等待边界

整个会话累计 **100+ 次** Stop hook 拦截，典型原文：

```text
Stop hook feedback:
mission is currently executing, not verified;
flow.sh next suggests: Merge U-01 into the integration branch;
science_gate.auditor=true but science-audit.md does not exist
```

```text
Stop hook feedback:
mission is currently reviewing, not verified;
flow.sh next suggests: Merge U-01 into the integration branch
```

后果：

- PM 在等待 executor/reviewer 时无法正常结束回合；
- 用户正在人工验证时，PM 被要求先合并；
- `reviewing` 被当成「必须 merge 才能结束」，把 H3 验收和 H2 合并耦合在一起；
- `science-audit.md` 要到 N5 才产出，却在 planning/gate/executing 阶段被反复报缺失。

### 1.2 派发边界

```text
Write ... is outside the current work unit scope; allowed:
PairingModels.py, SlotExtractor.py, AssemblyBuilder.py, ...
```

背景是 PM 已记录 D-027 授权扩 lane，但 `flow.json` 的 claim 没有同步，PreToolUse 守卫仍按旧写集拒绝。随后又出现：

- U-07 的 F-REV-45 已完成，但 executor 收到重复派发，回 `BLOCKED`：「本条为重复派发，未重做」；
- claim 已推进到 U-13，但 executor 没收到任务本体，连续三次停在「有 claim、无任务」；
- PM 判断「executor 的消息队列似乎仍在消化早前的重复派发（每次唤醒会处理一条旧消息）」；
- 最后释放并重取 claim，spawn 替代实例 `spec-executor-c`；
- 11-23 `Agent "Fork review U-07" failed: Agent stalled: no progress for 600s`；
- 11-25 用户一次性 stop 了 **31 个 background agents**。

### 1.3 授权边界

```text
R-10 要求 verdict 落盘，但写守卫的白名单只覆盖当前 executor
claim 的 verdicts/U-03.json，reviewer 只能用 V-01-U-01.json 落盘。
```

同类问题被登记为 D-011 / D-030。根因是写权限按「当前 claim 的 owned_files」计算，而不是按角色应有的输出目录计算。

### 1.4 验收边界

用户 11-19 连续追问：

> 为什么 chain pipeline 的结果 region 还是 Coiled coil? 而不是具体的 E 或 K? 到底有没有变为两个区域啊?

PM 的结论：模型层确实拆成了两个 region（`region_type=COILED_COIL` + `coil_type=E/K`），但 Web 层只读 `region_type`，把 E 块和 K 块合并成一条 "Coiled coil" bar。全量 3460 tests passed，但用户可见结果仍是错的，最终新开 ISS-006 并追加 Round 3 / U-21。

### 1.5 推送与人工闸门

```text
git push is forbidden: this workflow requires the PM to merge into
the integration branch
```

PM 每次只能让用户手动执行 `!git push origin main`；107、108、109 都出现「本地领先 origin N 个提交，未推送」。N2 硬门也反复等待 `confirmed`，用户多次输入「确认」后 Stop hook 仍显示 `N2 hard gate: waiting for user confirmed`。

### 1.6 命令路由

第二个会话 `3daceecb-584f-45b6-8dae-e500dbe40874` 只有 2 条消息：用户输入 `/leo-team-plugin:spec-team 接下来请检查待办清单...`，命令把整段文字当成新需求，进入 N0 而不是只读查询，会话随即中止。

## 2. 设计原则

```text
P1  等待是一等状态：wait 与 state 正交，等待不等于失败。
P2  授权只有一个计算源：claim 与 grants 合成 effective_write_set。
P3  派发幂等、租约可回收：dispatch id 去重，stale 自动恢复。
P4  验收覆盖可观察输出：command / artifact / observable 三类 AC。
P5  不引入新运行时：文件状态 + 脚本 + hook，无 daemon / SQLite / worktree。
```

对应四条既有公理：

```text
A1  权威属于层，不属于角色
A2  完成由 harness 捕获的证据判定，不由执行者叙述判定
A3  不可逆动作由工具级能力模型强制；未标注工具默认拒绝
A4  没有 eval，就没有资格谈自治
```

## 3. 核心模型

`run.json` 在现有字段上增加四个一等对象：

```json
{
  "state": "executing",
  "wait": {
    "kind": "agent",
    "ref": "WO-003",
    "since": "2026-11-25T16:20:00+00:00",
    "deadline": "2026-11-25T16:22:00+00:00",
    "resume_when": "lease active or recovery dispatched"
  },
  "leases": {
    "WO-003": {
      "agent": "sancai-executor-c",
      "attempt": 2,
      "heartbeat_at": "2026-11-25T16:21:40+00:00",
      "ttl_seconds": 120
    }
  },
  "dispatches": {
    "D-7f3a9c": {
      "wo": "WO-003",
      "attempt": 2,
      "task_sha": "sha256:...",
      "status": "started",
      "agent": "sancai-executor-c",
      "acked_at": "2026-11-25T16:20:30+00:00",
      "started_at": "2026-11-25T16:20:35+00:00"
    }
  },
  "authority": {
    "claim": {
      "wo": "WO-003",
      "role": "executor",
      "owned_files": ["src/a.py", "test/test_a.py"]
    },
    "grants": [
      {
        "decision": "D-027",
        "extra_files": ["src/c.py"],
        "status": "active"
      }
    ]
  }
}
```

### 3.1 `wait`

| 字段 | 含义 |
|---|---|
| `kind` | `human` / `agent` / `external` |
| `ref` | `H3`、`ESC-003`、`WO-003`、外部任务 id |
| `since` | 进入等待的时间 |
| `deadline` | 可选；超时后进入恢复流程 |
| `resume_when` | 人可读的恢复条件 |

规则：

- 同一时刻最多一个 `wait`；
- `wait.kind=human` 时 Stop guard 必须允许结束；
- `wait.kind=agent` 且 lease 未过期时允许结束；
- `wait.kind=agent` 且 lease 过期时，先写入 recovery dispatch，再允许结束；
- `wait` 不改变 `state`，只影响 Stop guard 和状态卡。

### 3.2 `leases`

| 字段 | 含义 |
|---|---|
| `agent` | 执行该 WO 的 agent 标识 |
| `attempt` | 第几次派发 |
| `heartbeat_at` | 最近一次心跳 |
| `ttl_seconds` | 租约有效期，默认 120 |

规则：

- `lease.agent` 必须等于 `dispatch.agent`；
- `dispatch.status=started` 才能有 lease；
- 心跳更新只允许当前 lease 持有者；
- 过期 lease 标记为 `stale`，不得继续写文件。

### 3.3 `dispatches`

| 字段 | 含义 |
|---|---|
| `wo` | Work Order |
| `attempt` | 从 1 开始 |
| `task_sha` | 任务正文哈希 |
| `status` | `created` / `delivered` / `acked` / `started` / `done` / `stale` |
| `agent` | 目标 agent |
| `acked_at` / `started_at` | 时间戳 |

规则：

- `dispatch_id = hash(run, wo, attempt, task_sha)`；
- 同一 id 重复投递只记录 first delivery，不重复执行；
- 新 attempt 必须显式 `retry`，生成新 id；
- `claim` 前置条件：存在 `status=acked` 且 `task_sha` 匹配的 dispatch。

### 3.4 `authority`

```text
effective_write_set =
    claim.owned_files
  ∪ { grant.extra_files | grant.status = active }
```

`role_outputs` 是独立表：

| 角色 | 可写目录 |
|---|---|
| executor | `effective_write_set` |
| verifier | `L2-harness/verdicts/<wo>.json` |
| auditor | `L2-harness/science-audit.md` |
| PM | 仅通过 harness 脚本写 `run.json` / evidence 元数据 |

## 4. 状态机

```text
              ┌──────────────────────────────────────────┐
              │  planning                                │
              │  N0/N1: intent, plan, tasks, decisions   │
              └───────────────┬──────────────────────────┘
                              │ H1 sign + clean tree
                              ▼
        ┌──────────────────────────────────────────────┐
        │  executing                                    │
        │                                               │
        │   wait = none    ──► dispatch / review         │
        │   wait = agent   ──► lease / heartbeat         │
        │   wait = human   ──► H2 escalation             │
        └───────────────┬──────────────────────────────┘
                        │ all WO in {verified, merged}
                        ▼
        ┌──────────────────────────────────────────────┐
        │  reviewing                                    │
        │  N5 audit + N6 acceptance                     │
        │  wait = human(H3) 允许正常结束会话             │
        └───────────────┬──────────────────────────────┘
                        │ H3 accept
                        ▼
                 accepted (terminal)

  any non-terminal ──► abandoned (audit chain kept)
```

关键变化：

1. `wait` 与 `state` 正交，`executing` 和 `reviewing` 都可以处于等待。
2. `verified` 与 `merge` 解耦：WO 通过 G0+G3 即为 `verified`；merge 是 H3 之后的独立 H2 动作。
3. `reviewing` 不再隐含要求 merge，因此不会出现「用户还没验收，Stop hook 却要求先合并」的死锁。

## 5. Stop guard 决策树

```text
Stop request
   │
   ├─ run terminal? ──────────────────────────► allow
   │
   ├─ wait.kind = human? ─────────────────────► allow
   │     print: Sancai waiting: H3 accept (12m)
   │
   ├─ wait.kind = agent, lease fresh? ────────► allow
   │     print: Sancai waiting: WO-003 executor-c
   │
   ├─ wait.kind = agent, lease stale? ────────► recover
   │     1. mark lease stale
   │     2. create recovery dispatch (attempt+1)
   │     3. allow
   │     print: recovered WO-003 -> attempt 3
   │
   ├─ actionable work not dispatched? ────────► block
   │     print: Next: dispatch WO-002
   │
   └─ otherwise ──────────────────────────────► allow
```

禁止：

- 只要 `state != accepted` 就 block；
- 把「下一步建议」当成「当前必须完成」；
- 在 `wait.kind=human` 时要求先 merge。

## 6. 阶段门禁矩阵

`science_gate` 与 artifact 检查按阶段区分「尚未到期」和「缺失」。

```text
                planning   gate   executing   reviewing
init.md            REQ      REQ      REQ         REQ
plan.md            SOON     REQ      REQ         REQ
tasks.md           SOON     REQ      REQ         REQ
decisions.md       SOON     REQ      REQ         REQ
science-audit      N/A      SOON     SOON        REQ
evidence           N/A      N/A      REQ         REQ
verdicts           N/A      N/A      REQ         REQ
acceptance-card    N/A      N/A      N/A         REQ
```

图例：`REQ` = 必须存在；`SOON` = 尚未到期，不报错；`N/A` = 本阶段不适用。

规则：

- `science_gate.auditor=false` 时 `science-audit` 整列为 `N/A`；
- 只有 `REQ` 缺失才阻止阶段推进；
- `SOON` 缺失只写入状态卡，不进入 Stop guard 的 block 条件。

## 7. 授权模型

```text
                 ┌──────────────────────┐
                 │  decisions.md        │
                 │  D-027 expand lane   │
                 │  status: active      │
                 └──────────┬───────────┘
                            │ grant --decision D-027
                            ▼
                 ┌──────────────────────┐
                 │  authority.json      │
                 │  claim: WO-003       │
                 │  owned: [a.py,b.py]  │
                 │  grants: [+c.py]     │
                 └──────────┬───────────┘
                            │ compute
                            ▼
             effective_write_set = owned ∪ grants
                            │
                            ▼
                 ┌──────────────────────┐
                 │  PreToolUse guard    │
                 │  path ∈ effective    │
                 │  and ∈ role_outputs  │
                 └──────────────────────┘
```

规则：

- `grant` 必须原子更新 `decisions.md` 与 `authority.json`；
- 撤销决策时同步把 grant 标为 `revoked`；
- 守卫只读 `authority.json`，不解析 Markdown；
- reviewer / auditor 的输出目录由 `role_outputs` 决定，不受 claim 影响。

## 8. 派发与租约

```text
PM tick
  │
  ▼
┌─────────────────────────────────────────────────────────┐
│ dispatch = hash(run, wo, attempt, task_sha)             │
│                                                         │
│  created ──► delivered ──► acked ──► started ──► done   │
│      │            │           │          │              │
│      │            │           │          └─ heartbeat    │
│      │            │           │             超时 -> stale │
│      │            │           └─ same id resend -> drop  │
│      │            └─ no ack timeout -> resend same id    │
│      └─ new attempt only via explicit retry              │
└─────────────────────────────────────────────────────────┘

claim precondition:
    dispatch.status = acked
    and dispatch.task_sha = current task body hash
```

规则：

- `max_active_agents` 默认 `1 writer + 1 verifier`；
- `tick` 从 WO DAG 计算下一批可执行动作，PM 只执行 `tick` 返回的动作；
- agent 失败（stall、400、402、连接拒绝）不改变 run 状态，只让 lease 过期并生成 recovery dispatch；
- 旧 agent 的 lease 被标记 stale 后，其写操作由守卫拒绝。

## 9. 验收证据链

### 9.1 AC 类型

```json
{
  "id": "AC-UI-1",
  "check": "observable",
  "run": "streamlit run app.py -- --probe coil_identity",
  "expect": "transcript contains 'E coil' and 'K coil'",
  "evidence": "observable/AC-UI-1.txt"
}
```

| 类型 | 证据 | 判定 |
|---|---|---|
| `command` | exit code + stdout/stderr | harness 执行并记录 |
| `artifact` | 文件存在 + 内容断言 | harness 读取并 hash |
| `observable` | CLI transcript / screenshot / DOM 文本 | harness 采集，verifier 核对 |

### 9.2 证据链

```text
executor done
   │
   ▼
G0  command AC    -> exit code / artifact hash
    artifact AC   -> file exists + assertion
    observable AC -> run UI/CLI, capture evidence
   │
   ▼
G3  verifier checks:
      evidence hash
      command text
      output assertion
      no executor narrative
   │
   ▼
H3  accept card lists every AC with its evidence,
    including user-visible output
```

规则：

- `observable` evidence 必须带采集命令、时间、hash；
- 没有 `observable` 证据时，UI/CLI 类 AC 不得标记为通过；
- verifier 的 verdict 必须引用 evidence 路径与 hash；
- H3 卡片展示 `observable` 证据摘要，人可在卡片上直接看到用户可见结果。

## 10. 人类触点与 release

人类只保留三个决策点：

```text
H1  Intent         assess -> candidates -> card -> record-intent
H2  Irreversible   escalation card -> native Allow/Deny -> token
H3  Accept         evidence card (incl. observable) -> accepted
```

release 作为一张 H2 卡：

```json
{
  "action": "release",
  "commands": [
    "git switch main",
    "git merge --no-ff sancai/<run>",
    "git tag sancai-<run>",
    "git push origin main"
  ],
  "diff_sha": "sha256:..."
}
```

规则：

- 一次 Allow 生成一个绑定整组命令与 diff_sha 的 token；
- 任一命令执行后 token 失效；
- 不再需要 `!git push` 手工补命令；
- 人拒绝时记录具体理由，run 保持当前状态。

## 14. 测试与 eval 指标

| 指标 | 目标 |
|---|---|
| Stop guard 误阻塞率 | 0（`wait.kind=human` 或 lease 新鲜时） |
| 重复派发执行率 | 0（同 dispatch id 只执行一次） |
| claim / decision 漂移次数 | 0 |
| stale lease 恢复时间 | ≤ 1 个 tick |
| observable AC 覆盖率 | 所有 UI/CLI AC 100% |
| 人工 push/merge 命令次数 | 0（只走 H2 原生授权） |
| 每需求人工往返次数 | 较 leo-team-plugin 基线下降 |

eval 场景：

1. 模拟一个「用户验收期间 Stop hook」场景，确认会话可正常结束；
2. 模拟同一 dispatch 重复投递 3 次，确认只执行一次；
3. 模拟 D-027 扩 lane，确认 claim 立即生效；
4. 模拟 reviewer 写 verdict，确认不被路径守卫拒绝；
5. 模拟 UI 输出与 AC 不符，确认 observable AC 失败并阻止 H3。

## 17. 开放问题

以下问题需要在 Phase 1 评审时裁决：

1. **是否引入 `tick` 调度器**：由 PM 主动调用 `tick`，还是 harness 在 Stop/PostToolUse 时自动计算下一批动作。
2. **并发上限**：默认 `1 writer + 1 verifier` 是否足够；是否允许同一时刻多个只读 verifier。
3. **observable evidence 存储**：transcript 存文本；screenshot 是否入库、存哪里、如何 hash 与脱敏。
4. **release plan 粒度**：merge/tag/push 是否必须绑定为一张卡，还是允许拆成三次 H2。
5. **`wait` 超时策略**：超时后自动 recovery，还是先进入 `wait.kind=human` 让 PM 决定。
